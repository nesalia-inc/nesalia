# Debugging Techniques and pdb

Debugging is the process of finding the root cause of bugs in our code. Rather than guessing or adding print statements everywhere, we use systematic techniques and tools that let us inspect program state, step through execution, and evaluate expressions while the program runs.

## Debugging Mindset

Effective debugging starts with a systematic approach. When we encounter a bug, we first form a hypothesis about what might be wrong, then we design a test or inspection that can confirm or disprove that hypothesis. We narrow down the possibilities rather than randomly changing code hoping the bug disappears.

A practical debugging workflow:

1. **Observe** — Confirm the bug exists and understand its symptoms
2. **Hypothesize** — Form a theory about the root cause
3. **Test** — Design a check that confirms or denies the hypothesis
4. **Isolate** — Narrow down to the exact location of the problem
5. **Fix** — Apply the correction and verify it works
6. **Reflect** — Understand why the bug occurred to prevent similar issues

This approach prevents the common mistake of making random changes without understanding the problem, which often introduces new bugs.

## Using print for Quick Debugging

The simplest debugging technique is adding print statements to see values at runtime. This works for quick checks but has limitations:

```python
def calculate_total(prices, tax_rate):
    print(f"Prices: {prices}")
    print(f"Tax rate: {tax_rate}")

    subtotal = sum(prices)
    print(f"Subtotal: {subtotal}")

    tax = subtotal * tax_rate
    print(f"Tax: {tax}")

    total = subtotal + tax
    print(f"Total: {total}")

    return total

calculate_total([10, 20, 30], 0.08)
```

Output:

```
Prices: [10, 20, 30]
Tax rate: 0.08
Subtotal: 60
Tax: 4.8
Total: 64.8
```

We can see exactly what values flow through the function. The limitation is that we must remember to remove these prints later, and they mix debugging code with production code.

A better approach uses a dedicated debug flag:

```python
import sys

def debug_print(*args, **kwargs):
    if "DEBUG" in sys.environ:
        print(*args, **kwargs)

debug_print("Prices:", prices)
debug_print("Tax rate:", tax_rate)
```

This pattern keeps debug statements and makes them easy to disable globally.

## The pdb Debugger

Python's built-in debugger is `pdb`, which provides interactive debugging with the ability to inspect variables, step through code, and evaluate expressions mid-execution.

### Setting Breakpoints

We insert a breakpoint by adding `breakpoint()` in our code:

```python
def calculate_tax(subtotal, tax_rate):
    breakpoint()  # execution pauses here
    return subtotal * tax_rate

def process_order(order_id, items):
    subtotal = sum(item["price"] for item in items)
    tax = calculate_tax(subtotal, 0.08)
    return {"order_id": order_id, "total": subtotal + tax}

process_order("ORD-123", [{"name": "Widget", "price": 25}])
```

When the script runs and reaches `breakpoint()`, execution stops and we see the pdb prompt:

```
> /path/to/script.py(3)calculate_tax()
-> return subtotal * tax_rate
(Pdb)
```

The `->` arrow shows the line about to execute.

### pdb Commands

At the `(Pdb)` prompt, we enter commands to control execution:

- `n` (next) — execute the current line and stop at the next line
- `s` (step) — step into a function call
- `c` (continue) — resume execution until the next breakpoint
- `p expr` (print) — print the value of an expression
- `pp expr` — pretty-print the expression value
- `l` (list) — show surrounding source code
- `w` (where) — show the call stack
- `u` (up) — move up in the call stack
- `d` (down) — move down in the call stack
- `q` (quit) — exit the debugger

### Inspecting Variables

At a breakpoint, we can inspect any variable in scope:

```
(Pdb) p subtotal
100
(Pdb) p tax_rate
0.08
(Pdb) pp locals()
{'subtotal': 100, 'tax_rate': 0.08}
```

`p` evaluates the expression and prints the result. `pp` formats the output more readably for complex data structures.

### Stepping Through Code

We use `n` to execute the current line and move to the next:

```
(Pdb) n
-> return subtotal * tax_rate
(Pdb) n
--Return--
> /path/to/script.py(4)calculate_tax()->8.0
```

We use `s` to step into a function call rather than executing it in one go:

```
(Pdb) s
--Call--
> /path/to/script.py(1)calculate_tax()
```

This drops us inside the function so we can debug its internals.

### Continuing Execution

Use `c` to let execution run freely until the next breakpoint or program exit:

```
(Pdb) c
```

Use `c` again to stop at the next breakpoint.

### Moving Up and Down the Stack

When we are inside a nested call, `w` shows the call stack:

```
(Pdb) w
  /path/to/script.py(9)process_order()
-> subtotal = sum(item["price"] for item in items)
  /path/to/script.py(4)calculate_tax()
    return subtotal * tax_rate
> /path/to/script.py(3)calculate_tax()
```

The `->` marks the current frame. We can move up with `u` to inspect caller variables:

```
(Pdb) u
> /path/to/script.py(9)process_order()
(Pdb) p items
[{'name': 'Widget', 'price': 25}]
```

And move back down with `d`:

```
(Pdb) d
> /path/to/script.py(3)calculate_tax()
```

### Quitting the Debugger

Use `q` to exit immediately and abort execution:

```
(Pdb) q
```

This stops the program completely. Use this when you have found the bug and want to exit without continuing.

## Post-Mortem Debugging

When a program crashes with an exception, we can enter the debugger automatically using `pdb.post_mortem()`. This lets us inspect the state at the moment of failure:

```python
import pdb
import traceback

def risky_function():
    data = [1, 2, 3]
    return data[10]  # IndexError: list index out of range

try:
    risky_function()
except Exception:
    pdb.post_mortem()
```

When the `IndexError` occurs, pdb opens with the traceback, allowing us to inspect variables in the failing frame:

```
> /path/to/script.py(5)risky_function()
-> return data[10]
(Pdb) p data
[1, 2, 3]
```

We immediately see that `data` only has three elements, so index 10 is out of range.

### Using pm() Convenience Function

Python provides `pdb.pm()` as a shortcut for `pdb.post_mortem()`:

```python
from pdb import pm

try:
    risky_function()
except Exception:
    pm()
```

This is slightly shorter to type when setting up post-mortem debugging.

## Command-Line Debugging with pdb

We can also run a script under pdb without modifying the source code:

```bash
python -m pdb script.py
```

This runs the script under debugger control. When the script finishes or crashes, pdb shows the traceback. This is useful for scripts that run quickly but crash unexpectedly.

### Setting Breakpoints with break

At the pdb prompt, we can set breakpoints by line number or function name:

```
(Pdb) break 5
Breakpoint 1 at /path/to/script.py:5
(Pdb) break calculate_tax
Breakpoint 2 at /path/to/script.py:1
```

Then use `c` to continue to the breakpoint.

### Conditional Breakpoints

We can make a breakpoint trigger only when a condition is true:

```
(Pdb) break 5, subtotal > 100
```

This stops at line 5 only when `subtotal` exceeds 100, which is useful when we only care about specific cases.

### Listing and Clearing Breakpoints

```
(Pdb) break
Num Type         Disp Enb   Address    What
1   breakpoint   keep yes   at /path/to/script.py:5
(Pdb) clear 1
Deleted breakpoint 1
```

Use `clear` to remove breakpoints we no longer need.

## Other Debugging Techniques

Beyond pdb, several techniques help us debug specific situations.

### Debugging with sys.settrace

The `sys.settrace` function registers a function that Python calls on every line of execution. pdb itself uses this mechanism internally:

```python
import sys

def trace_calls(frame, event, arg):
    if event == "call":
        print(f"Calling function: {frame.f_code.co_name}")
    return trace_calls

sys.settrace(trace_calls)

def add(a, b):
    return a + b

add(1, 2)
```

Output:

```
Calling function: add
```

This low-level tracing shows every function entry point, which is useful for understanding control flow in complex programs.

### Inspecting with dir() and vars()

When debugging, we often need to see what variables exist in a scope. `dir()` lists all attributes and methods of an object, while `vars()` returns the local variables dictionary:

```python
def inspect_scope():
    name = "Alice"
    age = 30
    print("Local variables:", vars())
    print("All names:", dir())

inspect_scope()
```

Output:

```
Local variables: {'name': 'Alice', 'age': 30}
All names: ['age', 'name', ...many built-ins...]
```

This is useful at a breakpoint where we want to see everything available in the current scope.

### Inspecting Exception Information

When an exception occurs, the traceback module lets us format exception info programmatically:

```python
import traceback
import sys

def safe_execute(func, *args, **kwargs):
    try:
        return func(*args, **kwargs)
    except Exception:
        traceback.print_exc()
        return None

safe_execute(divide, 10, 0)
```

The `traceback.print_exc()` prints the exception traceback, which is more informative than a bare `print(e)`.

## IDE Debuggers

Most IDEs (PyCharm, VS Code with Python extension, etc.) provide graphical debuggers that wrap pdb with visual controls. These typically offer:

- Click-to-set breakpoints in the editor
- A variables panel showing current scope
- A call stack panel showing the function call chain
- Step/continue/break buttons
- Watch expressions that evaluate on every stop

The underlying mechanism is usually pdb or a similar debugger, so understanding pdb commands helps even when using a GUI debugger.

## When to Use Each Technique

Different debugging situations call for different tools:

- **Quick variable checks** — use print statements or `p` in pdb
- **Understanding execution flow** — use pdb with `n` and `s` to step through
- **Crash analysis** — use `pdb.post_mortem()` or `pm()` to inspect the failing state
- **Production issues** — add logging that captures context (not pdb, which requires interaction)
- **Performance issues** — use profiling, not debugging; see the [Generators and Generator Expressions](../generators/index.mdx) section for performance patterns

## Common Bug Patterns and How to Find Them

Some bugs recur frequently in Python. Recognizing the pattern helps us find them faster.

### Off-by-One Errors

When iterating with range, off-by-one errors cause us to miss the last item or go one past the end:

```python
data = [1, 2, 3, 4, 5]

# Bug: misses the last item
for i in range(0, len(data) - 1):
    print(data[i])  # prints 1, 2, 3, 4 (not 5)
```

Using pdb to inspect `i` and `data[i]` reveals the boundary issue quickly.

### Mutable Default Arguments

A classic Python gotcha: default mutable arguments retain state across calls:

```python
def add_item(item, items=[]):  # Bug: shared list
    items.append(item)
    return items

print(add_item("a"))  # ['a']
print(add_item("b"))  # ['a', 'b'] - unexpected
```

Using pdb to inspect `items` after the first call shows the accumulated state.

### Variable Scope Issues

When a variable is not defined where we expect it:

```python
def process():
    if True:
        result = 42
    print(result)  # NameError if result used outside the if block
```

Using pdb to inspect locals before the `print` shows whether `result` exists.

### Debugging pytest Failures

When a pytest test fails, we can run just that test with pdb:

```bash
pytest --pdbrace test_file.py::test_name
```

This drops into pdb at the point of failure, letting us inspect state interactively.

Alternatively, in a failing test:

```python
import pdb; pdb.set_trace()
```

This stops at that line during the test run.

## Summary

- Debugging systematically narrows down the root cause of bugs through observation, hypothesis, testing, and correction
- `print` statements work for quick checks but leave debugging code mixed into production code
- `breakpoint()` stops execution and drops us into the pdb debugger, where we can inspect variables and step through code
- pdb commands: `n` (next line), `s` (step into function), `c` (continue), `p` (print), `pp` (pretty print), `l` (list), `w` (where), `u/d` (up/down stack)
- `pdb.post_mortem()` enters the debugger after an exception, allowing us to inspect the failing state
- `python -m pdb script.py` runs a script under debugger control without modifying source
- Conditional breakpoints (`break line, condition`) stop only when specific conditions are true
- `sys.settrace` provides low-level tracing of every function call
- Different debugging tools suit different situations: print for quick checks, pdb for interactive investigation, logging for production
